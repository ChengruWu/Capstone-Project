## 想解决的问题与实现

新人遇到启动报错时，需要组合配置、启动和日志资料；单靠模型常识容易遗漏步骤，也可能编造来源。本项目基于课程 Agent v1 扩展一个本地文档助手，读取求助文件、检索六份教学文档，再给出有来源的操作建议。资料中的应用是虚构教学项目，本助手不会实际启动应用或修改其配置。

本周实现了以下尝试：

- **Memory**：把偏好从字符串列表改成键值字典。同名键覆盖旧偏好，支持显式删除和重新加载；用临时文件与原子替换保存。记忆只存用户主动提供的回答偏好，不存项目事实。实验先保存详细风格，再覆盖为中文简短步骤，并删除一条临时偏好；最终任务均重新加载更新后的值。记录见 [memory_demo.json](results/memory_demo.json)。另外实际通过两个独立 CLI 进程执行了保存和 `--show-memory`。
- **两种 Tool**：`read_file` 真实读取 workspace 内的 UTF-8 任务文件；`search_knowledge` 返回检索原文、真实编号、来源、内容哈希与排名。保留路径边界，补充 Windows 盘符、UNC 和符号链接检查。工具错误回传模型，允许在总轮数内修正。
- **Knowledge / RAG**：复用课程六份 Markdown，覆盖启动、配置、端口排错、日志、示例数据和导出。采用 240 字符窗口、40 字符重叠；本次资料较短，实际得到六个片段。BGE 做 CLS pooling、L2 归一化及查询指令；新增中文 bigram / 英文标识符 BM25，再与向量排名做 RRF 融合（常数 60、top-k=3）。索引在内存中构建。
- **来源校验**：最终引用必须来自本次成功检索返回的 `[文件名.md#编号]`，拒绝虚构编号、任务文件编号和网页来源。默认至多反馈模型纠正一次；保存每轮 raw、工具返回、候选回答和失败原因，原始 JSON 不做人工改写。任务文件只是用户问题，不能作为知识证据。

## 环境与运行

复用仓库 `2026顶点课程/第一周_LLM推理/.venv`，未重装 PyTorch 或原有模型。回答模型复用 Qwen2.5-7B-Instruct，新增下载 BAAI/bge-small-zh-v1.5。核心环境：Python 3.12.1、PyTorch 2.4.0+cu121、Transformers 4.51.3、Accelerate 1.6.0、BitsAndBytes 0.45.5，GPU 为 RTX 4060 Laptop 8 GB。完整版本、执行参数和文件哈希见 [environment.json](results/environment.json)。

Qwen 使用 CUDA NF4 双重量化、BF16 计算、seed=42、贪心生成，每轮最多 768 个新 token，总上下文预算 8192、最多八轮。BGE 使用 CPU、float32、eager 注意力和单线程。

在 `solution/` 中，正式批量实验命令为：

```powershell
& '../../../2026顶点课程/第一周_LLM推理/.venv/Scripts/python.exe' -X utf8 run_experiments.py --output-dir results
```

复现时改用新的 `--output-dir results_reproduce`，避免覆盖原始记录。单次任务、依赖、模型路径、记忆操作与无模型测试命令见 [README.md](README.md)。提交包不含权重、虚拟环境或下载缓存。

## 实际结果

八个固定问题按人工指定的来源文件评估，结果见 [检索对照原文](results/retrieval_comparison.json)：

| 检索方式 | 首条命中 Hit@1 | 平均 Source Recall@3 |
| --- | --- | --- |
| BGE 向量 | 7/8（87.5%） | 100% |
| BM25 + BGE / RRF | 8/8（100%） | 100% |

差异出现在“修改 APP_PORT 后是否自动生效”：向量首条是 startup.md，混合检索将 configuration.md 排到首条；两者前三条都召回了该配置文档。八题太少，标签也是针对本知识库人工选定，不能据此声称混合检索普遍更优。

五次真实模型运行均实际读取任务文件并调用检索。端口两组的任务、记忆、模型、解码参数和来源纠正策略相同，只改变检索方式。表中 `ok` 仅表示编号检查通过。

| 场景与原始记录 | status | 决策轮数 / 来源纠正次数 | 人工核对效果 |
| --- | --- | --- | --- |
| [01 向量端口排障](results/01_vector_port.json) | ok | 3 / 0 | 端口值、启动命令和日志路径正确；遗漏旧实例先正常退出，启动命令引用定位不精确 |
| [02 混合端口排障](results/02_hybrid_port.json) | ok | 3 / 0 | 关键操作正确；同样遗漏旧实例退出，末尾集中列来源，未逐步对应 |

正式运行的来源编号检查通过 **4/5**，不能称为四次任务完全成功。综合任务只检索了安装主题，未继续补查日志；还把原文“若 8001 也被占用”写成 8000，并在前面给出 `logs/app.log` 后又称日志位置未知。日志保留天数确实未规定，日志位置则已有资料，不应混为未知。未知问题的纠正主要满足引用格式，没有证据表明提升了事实质量。

48 项无模型单元测试通过，覆盖记忆更新、路径边界、检索排序、工具失败反馈、原文留存和来源纠正等，日志见 [tests.log](diagnostics/tests.log)。正式记录的 **307 项完整性检查全部通过**：核对代码/知识库哈希、raw 与 messages、真实工具片段、记忆、逐题指标、汇总字段、引用重算及重复查询的共同片段向量分数；详见 [verification.json](results/verification.json)。这些是程序与记录检查，不等于模型回答全部正确。

## 遇到的问题与边界

第一次检索因 BGE 输出 NaN 终止。相同有限权重与输入下，默认 CPU SDPA 输出 9216 个非有限值，切为 eager 后没有 NaN，见 [兼容性诊断](diagnostics/bge_compatibility.json)。进一步复核发现，多线程 eager 虽然输出有限，同一查询仍会变化；1 线程下连续五次完全一致，且开启或关闭 MKLDNN 均一致。线程对照见 [稳定性诊断](diagnostics/bge_stability_probe.json)，最终配置验证见 [修复后验证](diagnostics/bge_stable_config.json)。这是本机环境观察，没有据此断言所有设备或版本都有相同问题。

NaN 初次失败保留在 `results_setup_failure/` 与 `setup_failure.log`。多线程不稳定的一轮保留在 `results_unstable_bge/` 与 `unstable_bge.log`，其检索指标不用于本报告结论。该轮还观察到导出任务只读取问题就回答，以及把任务文件编造成引用；程序将其标为 `citation_failed`。随后增强了任务文件与知识证据的区分，以及未检索时的纠正反馈，再用稳定配置完整重跑。

来源编号通过只说明可追溯，不能保证编号支持相邻事实或回答完整。单元测试专门展示了“错误事实附真实编号仍可能通过”的边界。无关问题仍会召回排名最高的资料，系统没有把相似度当可回答概率。偏好演示证明持久化、更新和加载，不是关于记忆提升回答质量的因果实验。
