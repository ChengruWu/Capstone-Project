## 1. 从 1.5B 开始：遇到了什么问题

最初沿用前两周的 Qwen2.5-1.5B-Instruct，在本机 CUDA 上以 BF16 运行 Agent。固定任务为“读取 test_report.txt，计算测试通过率”，工具工作目录中确实存在以下内容：

```text
passed=47
failed=3
```

正确答案是 `47/(47+3)*100 = 94%`。我们希望模型根据 read_file 的真实返回值，再调用 calculator 完成计算，最后输出 final。

最初五组实验均未完成任务。主要问题包括：

- **路径不遵循约束**：模型生成 /content/test_report.txt、/test_report.txt 等绝对路径，触发工具的路径安全校验，未成功取得报告。
- **未利用反馈修正参数**：工具 Observation 已提示使用相对路径，但模型仍重复错误路径，或把失败归因于环境权限。
- **输出格式不稳定**：部分轮次只有道歉、解释或推测，没有符合协议的 JSON 决策。
- **status=ok 不等于任务完成**：四组最终输出了可解析的 final，但内容是放弃任务或要求提供路径；另一组因连续失败终止。
- **提示词改动仍未解决问题**：额外明确相对路径后，模型仍使用 /test_report.txt，并在未读取文件的情况下给出没有工具依据的统计信息。

Agent 自测与工具校验通过，支持“问题出在这组模型输出和交互轨迹，而不是报告文件不存在”的判断。完整原文保存在 results/，本报告不修改实验 JSON。

#### 1.5B 第 1 次：贪心，status=ok，但任务未完成

1. **raw** 先说“需要先读取文件并计算测试通过率，请稍等。”，随后输出 `read_file` 调用，路径为 `/content/test_report.txt`。**decision** 带有模型自行补出的绝对路径；**observation** 是路径安全校验返回的 `PermissionError`。

第 2 次与第 1 次相比只开启了采样。该固定种子下，采样产生重复错误路径调用；这一次观察不能说明温度 0.7 普遍更差。

## 2. 为什么从 1.5B 换到 7B

在基础工具正常、五组解码参数调整及明确路径的提示词尝试仍不能完成任务后，我们把更大模型作为下一阶段的验证方向：重点观察它能否更好遵循工具参数约束、利用 Observation，并维持多步 JSON 决策。换模型并不预先保证正确，仍需用真实 trace 验证。

选择同一 Qwen2.5 Instruct 系列的 7B，是希望在本机资源范围内提高模型容量。3B 也可以作为候选，但本次没有下载或测试 3B，因此不声称 7B 一定优于本机运行的 3B。

本机为 i9-13900HX（24 核 / 32 线程）、16GB DDR5-5600、RTX 4060 Laptop 8GB。7B 的 BF16 权重约 15GB，无法完整放入 8GB 显存；因此采用加载时 NF4 4-bit 量化、double quantization 和 BF16 计算，把全部模型层放在 cuda:0。继续使用现有 Python/Transformers，只增加 bitsandbytes 和 accelerate 依赖，无需 Ollama。

官方原始文件约 15.24GB，保存在第一周 models/Qwen2.5-7B-Instruct；磁盘上保留的是原始权重，每次加载时再量化。下载时已按文件版本逐个校验 SHA-256，清单位于 logs_7b/model_download_manifest.json。模型下载现在直接使用 Hugging Face 官方 Python 接口，方法见 README。

模型来源：[Qwen 官方模型卡](https://huggingface.co/Qwen/Qwen2.5-7B-Instruct)；加载方案：[Transformers 4.51.3 量化说明](https://huggingface.co/docs/transformers/v4.51.3/quantization/bitsandbytes)。

## 5. 采样和温度究竟有没有生效

**第 2–5 组确实启用了采样，并把各自的 temperature、top-p、top-k 传给了模型生成函数；第 1 组为贪心解码，这三个参数不参与采样。** 两种模型都使用以下调参顺序：

| 组别 | sample | temperature | top-p | top-k | 相比上一组 |
| --- | --- | --- | --- | --- | --- |
| 1 | False | 不参与贪心解码 | 不参与 | 不参与 | 基线 |
| 2 | True | 0.7 | 0.8 | 20 | 仅开启采样 |
| 3 | True | 0.3 | 0.8 | 20 | 仅调整温度 |
| 4 | True | 0.3 | 0.95 | 20 | 仅调整 top-p |
| 5 | True | 0.3 | 0.95 | 50 | 仅调整 top-k |

代码依据见 [agent_v0.py](agent_v0.py) 的 make_hf_llm：sample=True 时构造 do_sample=True 及各采样参数，调用 model.generate 时通过 **gen_kwargs 传入；入口也将 CLI 参数传入该函数。实际参数可在每份结果的 config 与命令日志中逐项核对。第 1 组日志中“采样参数仅用于 sample 模式”的警告对应贪心基线，不表示第 2–5 组的参数被忽略。

**更准确的实验观察是：7B 第 2–5 组保存的生成文本（raw）、决策和工具返回相同，耗时等元数据不同。在本任务、固定 seed=42 的这几次运行中，没有观察到生成文本的变化。** 这不代表参数未生效，也不代表不同参数等价。温度调整概率分布，top-p/top-k 限制候选范围；这些变化不保证一次抽样的最终文本不同。固定种子用于复现随机过程，不会强制不同参数生成相同答案。

本次没有保存逐 token 的 ID、logits、概率或候选集合，因此不能根据相同 raw 断言各步概率分布相同，也不应表述为“已经逐 token 证明选择完全相同”。第 3 组参数仅作为已成功验证的后续起点，没有证据证明它优于第 2、4、5 组。

## 6. 两种模型的综合对比与结论边界

| 指标（各自基础五组） | 1.5B BF16 | 7B NF4 |
| --- | --- | --- |
| 成功读取报告的实验数 | 0/5 | 5/5 |
| 完整 read_file → calculator → final 且正确 | 0/5 | 4/5 |
| status=ok 的实验数 | 4/5 | 5/5 |
| 主要问题 | 错误路径、未利用反馈、非 JSON 解释 | 贪心组混淆协议、未调用计算器并算错 |
| 正确答案出现情况 | 五组均未给出正确通过率 | 四组采样实验均给出 94.0% |

在当前机器和任务下，7B 量化方案比此前 1.5B 方案更能完成实际工具调用，同时显存可容纳，因而选为后续使用方案。

跨阶段同时改变了模型规模、权重精度和生成上限，且代码增加了量化加载与上下文预算检查，所以这是一组实际方案对比，**不是仅改变模型规模的严格消融实验**。只能报告观察到的改善，不能把所有差异单独归因于参数量，更不能据单次固定种子实验推断普遍成功率。

### 7.2 JSON 停止条件对照

legacy 从第一个左花括号开始无条件计数，可能把字符串中的右花括号误认为对象结束；string-aware 增加 in_string 和 escaped 状态，忽略字符串内部花括号。此修复只决定生成何时停止，不代替 JSON/Pydantic 校验，不裁剪或改写 raw。

边界任务要求 answer 逐字等于“右花括号 } 是普通字符。”。两种模型的 legacy 首步 raw 均在 `{"action":"final","answer":"右花括号 }` 处提前停止，后续纠错仍因截断而失败，三步后 too_many_failures。string-aware 均在一步内返回完整 JSON 和正确字符串。这是代码边界修复对两种模型都有效的实际证据。

### 7.3 最终推荐配置的额外验证
